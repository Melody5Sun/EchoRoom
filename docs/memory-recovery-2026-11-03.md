# GC 存活对象与故障补偿续验

## 内存对比

无压测连接时逐实例执行 GC、类直方图及堆概况。最初 8 个 JVM 的 GC 前后堆合计约 519.3 → 252.8MiB，老年代约 335.9 → 247.9MiB；合计并非同一时刻的原子快照。

刷新隔离账号后建立干净基线，重放两轮相同负载：两个房间、100 条目标连接、10 个发布者、10 个暂停 TCP 读取的慢客户端，慢端开启 15 秒主动关闭看门狗、指数退避及随机抖动。每轮为短时 30/60/120 秒三阶段，不替代正式容量时长。

| GC 后指标（8 个 JVM 合计） | 干净基线 | 第一轮后 | 第二轮后 |
| --- | --- | --- | --- |
| 老年代 | 240.5MiB | 246.1MiB | 242.7MiB |
| 完整堆已用 | 243.2MiB | 250.0MiB | 245.7MiB |

三个采样的容器 startedAt 相同，没有用重启制造下降。两个 Live 的 RoomSessionRegistry$SessionState、SessionSender$Outbound 存活计数结束后均为 0。第一轮 Live 增量主要是整数数组，第二轮各回收约 2.8/3.0MiB；类计数不能独自确定引用根，但未见等量重放后单调累积的会话保留。

运行 20261103T083535Z、20261103T084607Z 的接收端三阶段握手均 100%，p95 分别为 86/60/94ms 和 114/106/97ms。独立审计应送达记录分别为 92059、92038，缺失均 0。每轮 120 秒确认阶段，慢端均完成 60 次打开和主动关闭，并执行重连调度；不把主动关闭算作服务端背压隔离。

诊断工具已实际验证：连接活动时拒绝强制 GC、退出 1、不生成报告。协议与命令边界见 [诊断手册](jvm-memory-diagnostics.md)。本次窗口未见持续抬升的 GC 后基线，但不能据此保证任意负载、无限时长绝无泄漏。

## 真实 ChatPanel 故障补偿

运行 browser-b9756431 使用真实 Edge、HttpOnly Cookie 登录、Ticket、数据库历史及 Redis 广播，未替换响应。

- 浏览器位于 Live1、独立发布者位于 Live2；重启 Live1，发布者持续发送。
- 实际创建 3 次 WebSocket、关闭 2 次，约 10314ms 恢复。该值是单次观察，不是恢复时间 p95。
- 90 条受理消息全部显示，其中 4 条未出现在浏览器直接接收的 WebSocket 帧中、最终经历史接口补回；渲染重复为 0。
- 恢复后通过真实输入框和发送按钮发送探针，页面显示成功。
- 关闭发布者、等待退订后，Live1 连接/订阅均 0，Live2 均 1，Redis 房间频道 NUMSUB=1，验证无观众节点不接收该频道。
- finally 恢复重启节点并关闭本次浏览器和发布端，两个 Live 均健康。

本演练验证重连、历史补偿、去重和动态退订，不验证交易故障账务，也不与正常稳态延迟混算。

## 交易阶梯中止与修复

正式运行 20261103T092524Z 因发现 Outbox 恢复死锁和不确定 HTTP 结果而人工中止，本轮没有批准任何容量档位。预热和 5 请求/秒阶段分别确认 1501、3000 个订单；7 请求/秒阶段 HTTP 确认 4174 次，另有 27 次系统错误，但数据库最终成功数为 4201。这 27 次请求不能因为后台最终成功就计作成功 HTTP。9 请求/秒和部分稳态数据只保留为诊断资料。

对账仅证明资金一致：本轮累计 14137 个 SUCCESS、28274 条唯一流水，送礼方合计扣减、主播增加和订单金额均为 14137。已中止阶段的客户端统计不完整；报告明确 accountingReconciled=true、capacityApproved=false，不能据此批准容量。

InnoDB 诊断显示旧的 SENDING 恢复范围 UPDATE 先持有状态索引锁，再等待主键，与按主键完成 Outbox 的更新发生锁顺序倒置。46a0368 将恢复改为有界、非锁定候选查询，再逐条按主键条件更新；V9 增加恢复索引，完成状态或刷新租期的并发操作不会被旧快照覆盖。真实 MySQL 测试覆盖新鲜发送行锁、分批恢复及快照竞态。完整 Java 门禁 43 项通过、零跳过，其中新增真实 Redis 频道迁移兼容矩阵 2 项；该矩阵不是生产滚动发布记录。

V9 已应用到本地 HA，两个 Live 均恢复健康。隔离探针 ambiguous-d18d8d09a2 暂时持有空 PENDING 索引范围 8 秒：2 次 HTTP 503、随后 2 个 SUCCESS、4 条唯一流水，双方余额各变化 2。新增 k6 指标 orders_ambiguous_accepted=2、orders_unconfirmed=0；HTTP 错误和交易延迟阈值仍判失败。固定 30 秒预算包含 POST 和终态查询，避免漏掉“接口失败、后台成功”的订单。
