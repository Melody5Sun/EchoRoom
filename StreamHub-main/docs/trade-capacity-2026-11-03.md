# 完整 HA 下的交易负载续验

本机验证通过每秒 7 次送礼、持续 30 分钟的档位。每秒 9 次档位出现 10 次 dropped_iterations，未通过；没有据此确定服务端容量上限。压测端与完整 HA 拓扑共用一台 Windows 主机，正式容量上限仍需独立压测机验证。

## 固定条件

- 运行编号：20261103T103406Z；开始提交 e0074f3，工作区当时干净。
- 16 个逻辑处理器、约 15.3GiB 宿主机内存；Docker 上限 12GB，实际约 11.68GiB。
- 三 MySQL/Router、三 Redis/三 Sentinel、双 Broker/三 Controller/双 NameServer、三 Nacos、双 SRS；8 个应用 JVM、双 Live、双 Gateway、双 Realtime。
- 使用 capacity、verify 和 verify-infra overlay 的实际限制；Live 最大堆 384MiB，其余应用最大堆 192MiB。基础设施共享 Docker 资源。
- 20 个充值参与者向同一主播、同一房间送礼。k6 为到达率模型，预分配 50、最大 200 VU；请求与终态查询共用 30 秒预算。
- 前后 8 个实际运行 JAR 哈希、应用镜像与资源参数一致；8 个应用启动时间均早于本轮开始。未在压力期间构建、替换运行产物或调整资源。
- 验证脚本与边界修复源码在等待期间继续编写，但未部署；后续 WS 订阅检查和前端边界修复不属于本轮运行产物。

9/s 阶段实际执行 5391 次，另有 10 次计划迭代未发起。22 次 HTTP 503 集中在一个突发窗口，均按原订单号找回 SUCCESS；错误率约 0.408%，仍保留为系统错误。没有未确认、FAILED、CLOSED 或超时 PENDING 订单。未发现 Live 死锁、Outbox 投递错误或 OOM 签名；当前证据不足以将该突发归因为单一组件。压测驱动及宿主机争用尚未排除，不能把 7/s 当作数据库或服务端极限。

脚本因 dropped_iterations=0 门禁失败停止加压，按前一档进行 30 分钟确认。未提高阈值，也未将 503、保护拒绝或未发起迭代计为成功 HTTP 承载量。

## 一致性与资源

全轮共 26673 个 HTTP 确认订单，加 22 个找回的后台订单，数据库为 26695 个 SUCCESS。53390 条流水的业务编号全部唯一；订单金额合计、发送方钱包扣减与主播钱包增加均为 26695。结束后 SQL 查询无未投递 Outbox。账务核验通过只证明资金一致，脚本本身不自动批准容量。

30 分钟确认期间 40 次资源采样，采样错误为 0，8 个应用目标始终 up：

- 连接池等待量始终 0，采样活动连接合计峰值 4；MySQL 运行线程峰值 9。
- Outbox 共享待投递数采样峰值 4、最老年龄始终 0 秒；消费者积压采样峰值 4，无持续增长。两份共享数据库计数不相加，消费者按组去重取最大值后汇总。
- 8 JVM 的堆合计在约 336.0～458.2MiB 波动，首末约 413.8→355.8MiB；老年代约 252.7→255.1MiB。该窗口未出现堆使用持续抬升，不构成长时间无泄漏保证。
- 宿主机可用内存约 0.371～2.004GiB，Docker VM 约 1.647～1.787GiB。这一共享环境不足以推导生产容量。

结束后在无压力、无待处理订单窗口执行存活对象诊断，结果另见 [内存与恢复续验](memory-recovery-2026-11-03.md)。强制 GC 不计入稳态测量。
